A pack is a folder with a pack.yml.

A pack bundles agents, content, skills and pages as one installable folder, and names anyone else's code by reference instead of copying it. pack_validate reads a pack folder and tells you, without running or fetching anything, what is wrong with it and what it would let loose on a Mac.

The manifest

pack.yml starts with pack_format: 1. Its parts are a tagged list; each has an id and a kind.

pack_format: 1
id: my-pack
name: My pack
version: 0.1.0
publisher: me
summary: What it is for.
license: MIT
requires:
  clis: [{ name: claude }]
  kit: { chat: 1 }
parts:
  - { id: all, kind: preset, includes: [helper, hello], default: true }
  - { id: helper, kind: agent, file: agents/helper/agent.yaml }
  - id: hello
    kind: skill
    source: commands/hello.md
    targets: [claude, codex, opencode]
setup_steps: ["setup/steps/*.yml"]

The kinds are preset, agent, content, skill, routine, dashboards, seed, external and setup. A skill part has one source file and a list of targets; the pack build writes a copy of it where each runtime looks for skills and commands. requires.kit names the dashboard kit modules the pack's pages use. The full field list is the exported schema, generated/schemas/pack-yml.schema.json; the lock a later install writes is packs-lock-yml.schema.json.

Other people's code is an external part

A pack never bundles a third-party file. An external part names an npm package or a git repository, pins a version plus a full 40-character commit (or the registry integrity), and says whether CodeSense maps files (method: files) or your agent runs the upstream installer (method: setup). It is declared and previewed; validation never fetches it. A bundled file under a third_party folder, a nested LICENSE file, or a SKILL.md whose license: differs from the pack's is refused with third_party_bundled.

Building a pack

node scripts/pack-build.mjs checks every pack's pack.yml against the schema, copies each skill part to each target runtime's location, and writes the files list: every bundled file with its sha256. --check changes nothing and fails when a copy was edited by hand or a file changed after the list was written.

pack_validate

Call pack_validate {path} with a pack folder inside a context repo you can read. It is read-only. It returns ok, a list of errors (each with a code, the path at fault and a message), warnings, the pack's parts and its risk facts.

{ "ok": false,
  "errors": [{ "code": "hash_mismatch", "path": "LICENSE",
               "message": "the file's sha256 differs from the one in files" }],
  "risk": { "executables": [], "cliHooks": [], "skipPermissionAgents": [],
            "mcpServers": [], "routines": [], "setupSteps": [], "networkFetches": [] } }

The rules it checks: every path is relative and under a declared root (content, panes, seed, agents, routines, roles, docs, media, commands, setup) with no symlink, .. or .git/; 5 MB per file and 200 MB per pack; every file listed in files with a matching hash; no unknown part id, duplicate or cycle in the parts graph; and external parts pinned. Each error code names its rule, for example symlink, path_traversal, file_unlisted, hash_mismatch, unknown_part, external_unpinned and third_party_bundled.

Risk is derived, never declared

The risk block comes from the files: executable files and scripts, CLI hooks, agents whose arguments skip permission checks, MCP servers, routines, setup steps (the exact upstream command your agent would run) and every network fetch an external part implies. A risk: key in pack.yml is ignored, with a risk_claim_ignored warning.
